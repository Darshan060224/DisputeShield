# Universal Dispute Control Architecture

## Product position

**DisputeShield is a merchant-side dispute-control system, not a dispute generator.** A customer may ask the merchant for help in Customer Space, but a local issue must never be represented as a Razorpay, bank, or card-network dispute. A real external dispute becomes actionable only when Razorpay provides a verified external record, preferably through a correctly signed webhook event.

> A dispute may be initiated by a customer through the issuing bank or by the issuing bank itself. Razorpay then notifies the merchant, including through subscribed dispute webhooks. [1]

| Channel | What it can create | Source label | Can it create a Razorpay dispute? |
|---|---|---|---|
| **Customer Space** | Local issue, document, return request, local resolution request | `customer_local_case` | **No** |
| **Seller Space** | Merchant record, fulfilment fact, local demonstration review | `merchant_record` or `demonstration_scenario` | **No** |
| **Razorpay API read** | Observed payment/dispute fact | `razorpay_api_observed` | **No** |
| **Signed Razorpay webhook** | Verified external dispute lifecycle change | `signed_webhook_verified` | **Yes — received, never generated by DisputeShield** |
| **Merchant approval** | Prepared evidence or acceptance decision | `merchant_approved` | **No automatic submission** |

## High-integrity dispute lifecycle

```text
Customer has a payment concern
        │
        ├─► Customer Space (optional local resolution)
        │       local issue / documents / return coordination
        │       └─► cannot create a bank, network, or Razorpay dispute
        │
        └─► Customer contacts issuing bank / issuing bank detects a concern
                    │
                    ▼
           Bank investigation and network process
                    │
                    ▼
           Razorpay dispute event
                    │
                    ▼
      Signed webhook at DisputeShield `/api/webhooks/razorpay`
                    │
      verify raw-body HMAC before parsing or persistence
                    │
                    ▼
   Verified Dispute Command Centre
     ├─ reason + phase + deadline normalization
     ├─ transaction/evidence graph
     ├─ missing-evidence checklist
     ├─ explainable recommendation and false-contest cost
     └─ merchant approval gate
                    │
                    ├─► accept/resolve path: merchant-controlled external action only
                    └─► contest path: merchant reviews prepared packet before submission
                    │
                    ▼
      Razorpay status webhook: under review / won / lost / closed
                    │
                    ▼
          Outcome ledger and operational-learning signals
```

Razorpay documents dispute phases as fraud, retrieval, chargeback, pre-arbitration, and arbitration. Its dispute entity also exposes a response deadline, status, reason code, evidence fields, and the deducted amount, which should be treated as external facts rather than model outputs. [2]

## Universal command-centre controls

| Control | High-standard behavior | Explicit prohibition |
|---|---|---|
| **Webhook trust gate** | Verify raw request body HMAC, deduplicate event IDs, retain source event reference, and reject invalid signatures before database writes | Never create a dispute from a customer UI click or unverified payload |
| **Reason intelligence** | Map the external reason code to a required-evidence checklist; allow AI only to extract bounded candidate facts from merchant-provided evidence | No fraud label, customer profiling, or automatic financial decision |
| **Evidence graph** | Join payment facts, order/fulfilment facts, customer communications, return/refund facts, and original document provenance | Do not invent delivery, refund, or customer-contact facts |
| **Decision support** | Explain readiness, uncertainty, deadline urgency, missing evidence, and false-contest cost | Do not claim a guaranteed win probability or auto-contest |
| **Merchant gate** | Require a deliberate merchant decision and a confirmation phrase before any external-ready packet is released | No automatic submission, refund, accept, or appeal |
| **Outcome truth layer** | Update outcome only from a verified Razorpay state/API fact or a signed webhook | Do not infer a win/loss from local workflow completion |

## Razorpay integration standard

The production activation must subscribe the **published DisputeShield URL** to dispute events such as `payment.dispute.created`, `payment.dispute.action_required`, `payment.dispute.under_review`, `payment.dispute.won`, `payment.dispute.lost`, and `payment.dispute.closed`. Razorpay’s webhook guidance requires signature generation against the **raw request body** and notes that retries for older deliveries may need the previous webhook secret. [3]

The dashboard can reconcile read-only facts through the Disputes API, but the webhook ledger remains the primary event-ingestion audit trail. Razorpay’s documented dispute entity includes both the external response deadline and evidence object fields, so the product should show those fields with source attribution and never relabel a local case as an external dispute. [2] [4]

## Implementation verification — 23 August 2026

The merchant dashboard now renders as a **Universal dispute command centre**. Its empty state explicitly says that Customer Space cannot create an external dispute and that signed webhook/API observations are the only external intake sources. The external queue is no longer restricted to a single reason label: the API mapper preserves the Razorpay reason code, phase, response deadline, observed evidence fields, and source boundary, while the existing evidence-policy engine remains conservative until verified delivery/address/payment facts are available.

The change was validated with 24 test files and 73 tests, TypeScript checking, production build, and an authenticated browser render. No new payment, refund, external dispute, evidence submission, or webhook delivery was initiated during this verification.

The webhook ledger is now merchant-scoped. For a configured owner merchant, a verified `payment.dispute.*` delivery retains its external dispute ID, reason code, phase, status, and response deadline after raw-body HMAC verification. The command centre prioritizes this signed record over a duplicate API observation of the same external dispute and shows its source as a signed Razorpay webhook. Other merchant identities receive an empty webhook-health result and cannot receive the configured merchant’s signed event facts.

Reason-specific policies now change the required evidence set without changing the safety posture. Refund-delay disputes require payment, refund-status, and communication facts; duplicate-payment disputes require payment, order, and reconciliation facts; unauthorized-transaction disputes require payment, checkout-authentication, and merchant records; wrong-amount disputes require payment, order, and invoice facts; and fulfilment-quality disputes require payment, delivery, and item-condition facts. Every unverified requirement remains an evidence gap and the external recommendation remains human review until a merchant deliberately approves a packet.

The signed-webhook projection is validated deterministically with merchant scope, valid signature state, malformed-payload rejection, latest-event selection, and duplicate suppression versus a Razorpay API observation. It is deliberately **not** represented as a live Razorpay delivery: only a separately configured, published webhook and a Razorpay Dashboard delivery can satisfy that final activation check.

The handler-to-command-centre regression now separately verifies the exact signed webhook persistence shape—merchant scope, external dispute ID, reason code, phase, status, deadline, and linked internal case reference—and verifies that a signed entry wins over an API observation with the same external ID. The complete deterministic suite passed with 26 test files and 78 tests, followed by TypeScript and production-build validation. This proof is deliberately local and deterministic; it does not claim a live Razorpay dispute was raised or delivered.
